```text

```

# System 6 — Adaptive newsroom intelligence and continuous improvement

## Objective

Build a controlled adaptive-learning system that improves from article evaluations, verification failures, compliance findings, revisions, rejected drafts, rescue outcomes, reader ratings, slider feedback, completion behavior, source performance, corrections, retractions, collaboration outcomes, production delays, formatting failures, publication performance, and human input.

The system may improve structure, length, technical depth, context, examples, workflow routing, source selection, evaluator calibration, revision targeting, assignment selection, personalization, timing, collaboration, failure detection, and format selection.

It must not silently rewrite code, policies, personas, compliance rules, thresholds, or infrastructure.

## Protected rules

Adaptive learning must never weaken factual accuracy, source requirements, verification, legal/medical/financial/defamation safeguards, privacy, fairness, uncertainty disclosure, required disclaimers, hard-fail rules, the 8.00 threshold, human authorization, editor identity, core personality, beat ownership, repository security, or permissions.

## Three-layer architecture

### Layer 1 — Immutable core identity

Persona files define identity, role, beat, personality, voice, interests, quirks, mannerisms, reporting instincts, evidence standards, boundaries, and anti-homogenization rules.

Automatic adaptation must not modify them. Core changes require proposed diff, justification, validation, approval, version number, Git commit, and rollback.

- target length;
- opening length;
- context level;
- technical depth;
- example placement;
- paragraph density;
- summary-box use;
- practical/analytical balance;
- preferred format;
- recurring confusion;
- successful structures;
- source recommendations;
- verification mistakes;
- collaboration needs;
- evaluator focus.

Scope by editor, beat, article type, audience, publication format, web/magazine, technical level, urgency, sensitivity, and length category.

### Layer 3 — Global newsroom learning

Learn broad patterns without erasing editor-specific voice. Examples: policy explainers improve when jurisdiction appears early; medical articles improve when evidence stage appears in the opening; breaking coverage fails less with primary sources; long pieces benefit from summary boxes; certain sources produce stale figures; certain image types crop poorly.

## Learning event ledger

Create `newsroom_learning_events` with:

- event ID;

- editor slug;
- article ID;

- beat;

- source system;

### Factual

### Stage 2 — Predictive models

# Final architectural principle and completion standard

The system improves through measured events, explicit mistake classifications, versioned lessons, explainable recommendations, controlled experiments, protected quality metrics, human approval, auditable changes, and reversible deployment.

It must not “self-improve” by silently rewriting itself.

It may evaluate prior outputs, identify recurring mistakes, maintain lesson memory, recommend adjustments, test approved changes, learn statistical patterns, improve routing, improve article structure, and improve generation guidance.

It must remain observable, versioned, governed, and reversible.

The completed platform should function as a connected intelligence system:

- Every article can become structured knowledge.
- Every material claim can be traced to evidence.
- Every major entity can maintain a living dossier.
- Every important change can update a timeline.
- Every comparison can expose its methodology.
- Every prediction can be remembered and resolved.
- Every major developing story can become a war room.
- Every reader can follow the exact entities and changes that matter.
- Every grounded answer can cite its evidence.
- Every magazine can become an interactive experience.
- Every useful journalistic insight can become a practical tool.
- Every correction and failure can improve future newsroom behavior.

Do not claim the master platform is complete merely because all routes exist. Completion requires production data integration, real provenance, stable IDs, working event propagation, secure access controls, successful builds, passing tests, responsive QA, documented update jobs, and no remaining mock-data dependency in production paths.
